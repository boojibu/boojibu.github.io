온체인 데이터 저장소를 고를 때 먼저 떠올리기 쉬운 조건은 데이터의 양이다. 블록이 생성될 때마다 거래와 이벤트가 추가되고, 분석할 기간이 길어질수록 조회해야 할 이력도 늘어난다. 이런 특성만 보면 대량 데이터를 빠르게 적재하고 집계하는 데이터베이스를 선택하면 될 것 같다.

그러나 같은 거래 이력을 저장하더라도 서비스가 묻는 질문에 따라 필요한 설계는 달라진다. 주소 하나의 최근 거래를 보여주는 화면과 수개월의 거래를 집계하는 대시보드는 읽는 범위부터 다르다. 여기에 토큰 정보나 주소 분류를 결합하면 데이터가 변하는 시점과 관계까지 고려해야 한다.

이 글에서는 **누적되는 거래·이벤트 이력과 비교적 예측 가능한 집계 요구**를 출발점으로 삼는다. 이 조건에서 어떤 후보를 검토할 수 있고, 조회에 맞춰 데이터를 미리 정리하는 접근이 왜 ClickHouse와 잘 맞는지 살펴본다.

> 초안의 범위: 조회 예시는 설명을 위해 새로 구성했다. 제품 비교는 2026년 9월 26일에 확인한 공개 문서를 바탕으로 하며, 도입 당시 모든 후보를 직접 시험했다는 뜻은 아니다. 성능 측정 결과와 실제 도입 회고는 아직 포함하지 않았다. `[작성자 메모]`는 경험을 보완할 자리다.

## 1. 먼저 서비스가 읽을 데이터의 모양을 정한다

비교를 위해 다음과 같은 조회를 가정해보자. 처음에는 거래 이력과 정해진 통계가 중심이고, 새로운 종류의 탐색 조건이 수시로 추가되는 상황까지는 전제하지 않는다.

| 조회 예시 | 주로 읽는 데이터 | 설계에서 확인할 점 |
| --- | --- | --- |
| 특정 주소의 최근 거래 목록 | 주소와 기간으로 좁힌 거래 이력 | 필터, 정렬, 페이지네이션에 필요한 접근 경로 |
| 토큰별 일간 전송 건수 | 기간 내 이벤트와 토큰 식별자 | 읽는 열과 범위, 반복 집계의 비용 |
| 한 토큰의 기간별 전송 수량 | 해당 토큰의 수량과 시각 | 수량의 정밀도, 단위, 중복 여부 |
| 신규 데이터 반영과 과거 이력 재수집 | 최근 구간과 과거 구간의 데이터 | 조회와 적재의 자원 경쟁, 재처리 결과의 일관성 |

주소별 목록은 작은 결과를 빠르게 반환해야 하지만, 작은 결과가 곧 적은 데이터 읽기를 뜻하지는 않는다. 저장된 데이터의 정렬 순서가 조회 조건과 맞지 않으면 몇 건을 찾기 위해 넓은 범위를 읽게 된다. 반대로 기간별 집계는 많은 행을 읽더라도 필요한 열이 제한적이고 계산을 나누어 처리할 수 있다.

따라서 하나의 평균 응답시간만으로 후보를 평가하기 어렵다. 목록과 집계가 각각 어느 범위까지 읽는지, 적재가 진행되는 동안에도 목표 응답시간을 지키는지 확인해야 한다. 이 글의 초기 조건에서는 다양한 관계를 조합하는 자유도보다 **자주 실행할 조회의 비용을 예측하고 줄이는 능력**에 무게를 둔다.

> **[작성자 메모 1]** 당시 가장 중요했던 조회를 일반적인 문장으로 두세 개 보완한다. 처음부터 필요했던 기능과 나중에 생긴 기능을 구분하고, 수치가 없어도 어떤 요구를 우선했는지 설명한다.

## 2. 누적되는 이력에도 정확성의 기준이 필요하다

거래 이력은 시간을 따라 추가되는 형태로 다루기 쉽다. 다만 분석 저장소에 들어온 모든 행을 영구히 확정된 사실로 취급할 수 있는지는 별개의 문제다. 예를 들어 Ethereum의 조회 API는 블록 기준을 `latest`, `safe`, `finalized`로 구분한다. 최신 블록을 얼마나 빨리 보여줄지에 따라 서비스가 다뤄야 할 정정 가능성도 달라진다. [Ethereum JSON-RPC의 블록 파라미터](https://ethereum.org/developers/docs/apis/json-rpc/)

여기에 수집기의 재시도로 생기는 중복, 누락 구간의 재수집, 파싱 방식 수정으로 인한 재가공이 더해질 수 있다. 원본 사건이 유지되는 경우에도 분석 저장소의 표현은 바뀔 수 있다는 뜻이다.

이 글에서는 일정한 확정 기준을 통과한 이력을 중심으로 분석하는 조건을 가정한다. 그래도 같은 사건을 다시 넣었을 때 건수나 합계가 늘어나지 않는지, 잘못 해석한 구간을 다시 만들 수 있는지는 확인해야 한다. 처리량을 비교하기 전에 두 후보가 같은 사건 집합을 같은 기준으로 집계하는지부터 맞춰야 한다.

## 3. 후보마다 어떤 비용을 먼저 확인할 것인가

데이터베이스를 비교할 때 기능의 존재만 확인하면 차이가 잘 드러나지 않는다. 집계, JOIN, 갱신은 여러 제품에서 지원한다. 여기서는 초기 조회를 구현하는 데 필요한 데이터 모델과 추가 작업을 함께 비교한다.

| 후보 | 이 글의 요구에서 검토할 이유 | 먼저 확인할 비용과 조건 |
| --- | --- | --- |
| PostgreSQL | 주소별 조회, 데이터 갱신과 관계 표현을 한 환경에서 구현 | 큰 범위 집계와 인덱스 유지가 동시에 발생할 때의 자원 사용 |
| ClickHouse | 누적 이력의 열 단위 조회, 반복 집계의 사전 계산 | 정렬 키와 조회의 일치, 중복 제거, 사전 가공 결과의 유지 |
| StarRocks | 집계와 다중 테이블 결합, 최신 상태 테이블을 함께 검토 | 데이터 분산과 JOIN 계획, 갱신 비용, MV의 갱신 정책 |
| Apache Doris | 분석과 키 기반 갱신을 함께 다루는 다른 후보 | 테이블 모델, 부분 갱신, 선택한 배포 구성의 운영 비용 |
| Iceberg + Trino | 이력을 파일 기반으로 보관하고 여러 분석에서 공유 | 파일·카탈로그 관리, 작은 적재 묶음, 서비스 조회 지연 |
| Parquet + DuckDB | 작은 범위의 분석과 재현 실험을 간단히 시작 | 실제 서비스의 동시 조회·지속 적재 요구를 별도로 충족할 방법 |

표는 성능 순위가 아니다. 같은 데이터를 넣었을 때 어느 제품이 빠른지는 각 후보에 맞는 설계와 동일한 결과 기준을 갖춘 실험으로 확인해야 한다.

### PostgreSQL: 기본 요구를 얼마나 오래 만족시킬 수 있는가

PostgreSQL은 먼저 비교해볼 만한 기준점이다. 주소와 기간에 맞는 인덱스를 두고, 거래와 메타데이터의 관계를 표현하는 접근부터 시작할 수 있다. 인덱스는 필요한 행을 찾는 비용을 줄이는 대신 저장과 갱신의 부담을 추가한다. [PostgreSQL 인덱스 문서](https://www.postgresql.org/docs/current/indexes.html)

검토할 질문은 데이터가 어느 행 수를 넘으면 사용할 수 없는가가 아니다. 실제로 자주 실행하는 집계가 읽는 범위, 목록 조회와의 자원 경쟁, 유지할 인덱스의 수가 목표와 맞는지다. 이미 PostgreSQL을 운영하는 팀이라면 다른 시스템을 추가하는 비용도 비교에 포함해야 한다. 초기 데이터가 작고 조회 요구가 제한적이라면 익숙한 환경에서 시작하는 선택이 유리할 수 있다.

### ClickHouse: 반복되는 읽기에 맞춰 데이터를 준비한다

ClickHouse의 저장 구조와 실행 방식은 필요한 열을 읽고 많은 행을 계산하는 분석에 초점을 둔다. 정렬과 인덱스로 읽을 범위를 줄이고, 열별 압축과 병렬 실행을 활용한다. 이 특성은 거래 이력에서 몇 가지 열을 읽어 기간별·토큰별로 집계하는 요구와 연결된다. [ClickHouse의 저장·쿼리 처리 구조](https://clickhouse.com/docs/get-started/about/why-clickhouse-is-so-fast)

반복할 집계를 미리 정할 수 있다면 증분 Materialized View도 검토할 수 있다. 새로 들어온 데이터 묶음에 계산을 적용하고 결과를 별도 테이블에 쌓는 방식이다. 조회 시 읽을 데이터를 줄일 수 있지만, 계산과 추가 저장의 비용은 적재 과정에서 부담한다. [ClickHouse 증분 Materialized View](https://clickhouse.com/docs/concepts/features/materialized-views/incremental-materialized-view)

이 글의 초기 조건에서는 이 비용 배분이 중요한 선택 근거다. 자주 실행할 질문이 분명하다면, 같은 결합과 집계를 매번 수행하는 비용을 적재와 사전 가공으로 옮기는 설계를 검토할 수 있다. 그 설계를 유지할 수 있는지는 뒤에서 다시 살펴본다.

### StarRocks와 Apache Doris: 결합과 갱신의 비중을 함께 본다

StarRocks는 여러 테이블의 JOIN과 집계를 Materialized View로 가속하고, 조건이 맞는 쿼리를 해당 뷰로 자동 재작성하는 기능을 제공한다. 조회 시점에 여러 관계를 조합해야 한다면 초기부터 중요한 비교 후보가 된다. [StarRocks MV 기반 쿼리 재작성](https://docs.starrocks.io/docs/using_starrocks/async_mv/use_cases/query_rewrite_with_materialized_views/)

키별 현재 상태를 유지하는 모델도 비교할 수 있다. StarRocks의 Primary Key 테이블은 같은 키에 대한 새 데이터를 기존 행의 대체로 처리한다. Apache Doris 역시 Unique Key 모델에서 UPSERT와 부분 갱신을 제공한다. 두 제품을 같은 것으로 취급할 수는 없지만, 이력 분석에 갱신 요구가 결합될 때 함께 검토할 후보라는 공통점은 있다. [StarRocks Primary Key 테이블](https://docs.starrocks.io/docs/table_design/table_types/primary_key_table/), [Apache Doris 갱신 모델](https://doris.apache.org/docs/3.x/data-operate/update/update-overview/)

초기에 조회 종류가 적고 사전 가공으로 대부분을 처리할 수 있다면, 이 기능들이 선택을 결정하는 기준이 아닐 수도 있다. 반대로 메타데이터를 자주 바꾸거나 새 관계를 계속 결합해야 한다면 비교의 비중이 커진다. 후보의 기능과 서비스가 그 기능을 필요로 하는 정도를 함께 봐야 한다.

### 파일 기반 분석: 보관과 조회를 나누어 생각한다

Iceberg는 파일을 테이블로 관리하기 위한 형식이고, Trino는 이를 조회하는 엔진이다. 하나의 데이터베이스 제품과 일대일로 대응하지 않는다. Trino의 Iceberg 커넥터는 오브젝트 스토리지의 데이터 파일과 카탈로그를 이용한다. 장기 이력을 여러 분석 도구가 공유해야 한다면 이런 구성도 검토할 수 있다. [Trino Iceberg 커넥터](https://trino.io/docs/current/connector/iceberg.html)

다만 API의 응답시간을 만족하는지는 별도로 측정해야 한다. 파일 수와 크기, 적재 주기, 캐시 상태까지 포함한 결과가 필요하다. 이력을 보관하는 계층과 서비스에 빠르게 응답하는 계층을 나누는 설계도 가능하지만, 계층이 늘어나는 만큼 동기화와 운영 작업이 생긴다.

개인 실험에서는 Parquet와 DuckDB를 기준 구현으로 사용할 수 있다. DuckDB는 Parquet를 직접 읽고 필요한 열과 필터를 스캔에 반영할 수 있다. 동일한 입력으로 기준 결과를 계산하는 데 활용하되, 실제 서비스 환경의 동시 부하를 검증했다는 의미로 확대하지 않는다. [DuckDB Parquet 지원](https://www.duckdb.org/docs/current/data/parquet/overview)

> **[작성자 메모 2]** 당시 실제로 검토한 후보와 이 글을 준비하며 추가한 후보를 구분한다. 운영 경험, 도입 일정, 사용할 수 있었던 환경 등 선택에 영향을 준 조건을 보완한다. 현재 문서의 기능이 당시 버전에도 있었는지는 별도로 확인한다.

## 4. JOIN을 줄인다는 것은 계산할 시점을 정하는 일이다

여기서 말하는 넓은 테이블, 즉 wide table은 조회에 함께 필요한 속성을 한 행에 모은 모델이다. 예를 들어 설명용 이벤트 모델에 시각, 자산 식별자, 송수신 주소, 원시 수량을 함께 두면 그 범위의 조회는 다른 테이블을 결합하지 않고 처리할 수 있다. 모든 데이터를 하나의 거대한 테이블로 합쳐야 한다는 뜻은 아니다. 한 행이 어떤 사건을 나타내는지부터 분명해야 한다.

조회마다 동일한 정보를 결합한다면 이를 미리 준비하는 편이 유리할 수 있다. ClickHouse 공식 문서도 관계가 지나치게 복잡하지 않고 데이터 변경이 드물거나 배치 갱신을 허용할 수 있을 때 비정규화를 고려하도록 설명한다. [ClickHouse JOIN과 비정규화 지침](https://clickhouse.com/docs/concepts/best-practices/minimize-optimize-joins)

이 선택은 세 가지 질문으로 점검할 수 있다. 미리 붙이는 속성은 얼마나 자주 바뀌는가. 한 사건에 연결되는 값이 여러 개일 때 행이 늘어나 합계가 중복되지 않는가. 새로운 필터가 생겼을 때 기존 테이블로 지원할 수 있는가.

가령 한 주소에 분류가 여러 개 달릴 수 있다면, 거래마다 분류를 모두 펼친 테이블의 수량을 그대로 더해서는 안 된다. 어떤 분류를 기준으로 중복을 허용할지, 거래와 분류의 관계를 별도로 유지할지 정해야 한다. 이런 문제는 제품의 처리 속도보다 결과의 의미에 가깝다.

초기의 조회가 안정적이라면 조회별 테이블을 준비하는 접근을 선택할 수 있다. 대신 저장 공간, 적재 지연, 재생성 절차를 비용으로 기록해야 한다. 나중에 요구가 바뀔 때 비교할 대상은 이 비용까지 포함한 전체 설계다.

## 5. 이 조건에서 ClickHouse를 선택하는 근거

이 글에서 설정한 요구라면 ClickHouse를 우선 구현 후보로 둘 근거가 있다. 누적되는 사건 이력을 중심으로 필요한 열과 범위를 읽고, 반복되는 집계는 미리 계산하며, 조회에 맞춘 데이터 모델을 유지하는 접근이 가능하기 때문이다.

선택의 전제는 분명하다. 주요 조회를 어느 정도 예측할 수 있고, 자주 변하는 속성을 모든 과거 행에 복제하지 않아도 되며, 적재 단계의 추가 계산을 감당할 수 있어야 한다. 이 전제가 바뀌면 같은 기능 목록을 놓고도 평가 결과가 달라질 수 있다.

최신 상태나 중복 처리까지 맡긴다면 엔진의 의미도 확인해야 한다. `ReplacingMergeTree`에서는 같은 정렬 키의 여러 버전을 적재할 수 있고, 병합 전에 일반 조회가 중복 행을 반환할 수 있다. 조회 시 정확한 결과가 필요하면 `FINAL` 등의 전략과 비용을 고려해야 한다. 최신 행을 자동으로 한 번만 읽는다는 가정으로 설계해서는 안 된다. [ReplacingMergeTree 조회와 중복 제거](https://clickhouse.com/docs/concepts/features/operations/update/replacing-merge-tree)

> **[작성자 메모 3]** 실제로 ClickHouse를 선택한 결정적 이유를 보완한다. 당시 확인한 근거, 판단만 했던 부분, 도입 후에야 알게 된 제약을 각각 구분한다. 이 문단은 실제 경험이 들어간 뒤 회고형 문장으로 다듬는다.

## 6. 선택을 설명하려면 무엇을 검증해야 하는가

아직 이 초안에는 성능 비교 결과가 없다. 비교 실험에서는 먼저 동일한 입력이 동일한 결과를 만드는지 확인하고, 그다음 실제 조회 패턴에 가까운 성능을 측정해야 한다.

| 검증 항목 | 확인할 내용 |
| --- | --- |
| 정확성 | 중복 적재·재처리 전후의 사건 수와 합계가 같은가 |
| 조회 지연 | 목록과 집계의 p50·p95·p99가 각각 어떤가 |
| 데이터 반영 | 데이터 도착부터 조회 가능해지기까지 얼마나 걸리는가 |
| 동시 작업 | 실시간 적재와 과거 이력 재적재 중 조회가 어떻게 변하는가 |
| 전체 비용 | 원본·파생 테이블·인덱스·복제본과 가공 작업까지 얼마나 필요한가 |

제품에 맞게 정렬과 집계 구조를 최적화하되, 사전 계산을 사용했다면 그 계산 시간과 수정 비용도 포함한다. 하드웨어, 버전, 복제와 내구성 조건, 데이터 분포, 캐시 상태를 기록해야 다른 사람이 결과를 해석할 수 있다. 단일 집계 쿼리의 속도만으로 서비스 전체의 적합성을 결론내리기는 어렵다.

1편에서 설명한 선택은 누적 이력과 예측 가능한 조회를 중심으로 한다. 다음 글에서는 가격과 분류 정보, 최신 상태처럼 다른 시점에 바뀌는 데이터가 결합될 때 평가 기준이 어떻게 달라지는지 살펴본다.
