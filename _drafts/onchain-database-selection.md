온체인 데이터를 다루는 서비스를 만들 때, 데이터베이스 선택은 쉽게 데이터의 양에 관한 문제로 좁혀진다. 블록이 생성될 때마다 거래와 이벤트가 쌓이고, 분석할 기간이 길어질수록 보관할 이력도 늘어난다. 그러니 많은 데이터를 빠르게 저장하고 집계하는 데이터베이스가 필요하다는 결론에 도달하기 쉽다.

그런데 같은 이력을 저장해도 서비스가 묻는 질문은 서로 다르다. 특정 주소의 최근 거래를 보여주는 일, 토큰의 일간 전송량을 계산하는 일, 주소의 현재 잔액을 반환하는 일은 읽어야 할 범위와 결과를 만드는 방식이 다르다. 여기에 가격이나 주소 분류를 결합하면 과거의 사건과 나중에 바뀐 정보를 어느 시점의 기준으로 연결할지도 정해야 한다.

처음 ClickHouse를 도입할 때 주목했던 것은 **계속 쌓이는 이력과, 그 이력에서 반복해서 계산할 조회**였다. 자주 필요한 정보를 조회 요구에 맞는 테이블로 준비하면, 매번 여러 테이블을 JOIN할 필요는 크지 않을 것이라고 보았다. 조회 단계의 결합을 줄이는 방향으로 테이블을 설계한 배경이다.

이 글에서는 그 판단을 요구사항부터 풀어본다. 먼저 OLTP 중심의 저장소에 더해 OLAP을 검토할 이유를 살펴보고, 후보마다 어떤 비용을 확인해야 하는지 비교한다. 이어서 ClickHouse의 특성과 조회 중심 설계가 맞닿는 지점, 그리고 그 선택이 성립하려면 유지되어야 할 전제를 정리한다.

> **초안 안내** — 도입 배경은 현재까지 정리한 초기 판단에 한정한다. 제품 비교는 2026년 9월 26일에 확인한 공개 문서를 바탕으로 재구성했으며, 모든 후보를 도입 당시에 직접 시험했다는 뜻은 아니다. 아래 조회 예시는 설명용이고, 실측 성능이나 구체적인 운영 경험은 아직 포함하지 않았다.

## 1. 같은 온체인 데이터에도 서로 다른 조회가 있다

저장소를 비교하려면 먼저 서비스가 어떤 결과를 반환해야 하는지 정해야 한다. 이 글에서는 다음과 같은 조회를 예로 든다.

| 조회 | 읽기와 계산의 성격 | 먼저 확인할 조건 |
| --- | --- | --- |
| 특정 주소의 최근 거래 목록 | 주소와 기간으로 좁히고 최근순으로 정렬 | 필터에 맞는 데이터 배치, 페이지네이션 |
| 토큰별 일간 전송 건수와 수량 | 기간 내 사건을 읽어 그룹별로 집계 | 읽는 열과 범위, 반복 집계 비용 |
| 주소·토큰·분류를 조합한 탐색 | 이력과 참조 데이터를 결합 | JOIN의 입력 크기, 관계의 중복, 변경 반영 |
| 주소·자산별 최신 상태와 잔액 | 키마다 유효한 최신 값을 선택 | 상태의 버전, 갱신 순서, 조회 시점의 일관성 |

최근 거래 목록은 결과가 적더라도 반드시 가벼운 조회는 아니다. 주소와 시간 조건으로 읽을 범위를 충분히 줄이지 못하면, 몇 건을 반환하기 위해 많은 데이터를 읽거나 정렬할 수 있다. 반대로 기간 집계는 많은 행을 읽더라도 필요한 열이 제한적이고 반복되는 계산을 미리 준비할 수 있다.

현재 잔액은 또 다른 문제다. 사건이 발생할 때마다 행을 추가하는 이력과, 특정 시점의 상태를 하나의 값으로 보여주는 모델은 구분해야 한다. 잔액을 어떤 입력으로 계산할지는 체인과 자산의 특성에 따라 정의해야 하며, 모든 자산의 잔액을 전송 이벤트의 단순 합계로 얻는다고 가정하지 않는다.

따라서 API를 제공한다는 사실만으로 저장소의 성격을 결정할 수는 없다. 통계 API는 사용자가 직접 호출하는 서비스 기능이면서 넓은 이력을 계산하는 분석 쿼리일 수 있다. 중요한 것은 반환 형식보다 그 결과를 만들기 위해 수행하는 작업이다.

이번 글에서는 이 중 **누적 이력과 반복 집계에 무게를 둔 초기 선택**을 다룬다. 관계 결합과 최신 상태 조회의 비중이 커질 때 선택 기준이 어떻게 달라지는지는 2편에서 이어간다.

{% comment %}
경험 보강 1 — 당시 가장 중요했던 조회를 두세 개 적는다. 처음부터 필수였던 기능과 나중에 중요해진 기능을 구분한다. 일반적인 사용자 질문으로 표현하고 실제 SQL이나 내부 화면을 옮기지 않는다.
{% endcomment %}

## 2. OLTP에서 OLAP으로 검토 범위를 넓힌 이유

온체인 데이터에 거래가 많다는 설명과 데이터베이스가 트랜잭션 처리에 적합해야 한다는 설명은 서로 다른 문제다. 거래는 저장하는 데이터의 내용이고, OLTP와 OLAP은 그 데이터를 처리하는 패턴을 가리킨다.

OLTP는 소수의 레코드를 읽고 변경하는 짧은 트랜잭션을 중심으로 한다. OLAP은 넓은 범위를 읽어 필터링하고 집계하는 분석 작업에 초점을 둔다. 예를 들어 거래 한 건의 상세 정보를 가져오는 일과 여러 달의 전송 이력을 날짜별로 계산하는 일은 같은 원본을 사용해도 접근 패턴이 다르다. [ClickHouse의 OLTP·OLAP 설명](https://clickhouse.com/docs/get-started/about/intro)

여기서 별도의 분석 저장소를 검토할 이유는 데이터가 계속 늘어난다는 사실에 더해, **누적된 범위를 반복해서 읽고 계산해야 한다는 점**에 있다. 일간 통계 화면에 표시할 결과가 수십 행이라고 해도, 그 결과를 매번 원본에서 만든다면 계산에 참여하는 사건은 훨씬 많을 수 있다.

열 지향 저장소는 이런 작업에서 검토할 가치가 있다. 토큰별 전송량을 계산할 때 필요한 값이 토큰 식별자, 시각, 수량이라면 해당 열을 중심으로 읽을 수 있다. 같은 종류의 값을 모아 저장하는 압축 방식과 여러 행을 묶어 처리하는 실행 구조도 활용할 수 있다. ClickHouse는 열 지향 저장, 데이터 건너뛰기, 벡터화와 병렬 실행을 조합한다. [ClickHouse 저장·실행 구조](https://clickhouse.com/docs/get-started/about/why-clickhouse-is-so-fast)

그렇다고 PostgreSQL에서 집계를 할 수 없거나, 특정 행 수를 넘으면 반드시 다른 저장소로 이전해야 하는 것은 아니다. PostgreSQL도 병렬 쿼리를 제공하며, 인덱스와 데이터 모델을 조정해 요구를 충족할 수 있다. 별도 저장소를 도입하면 데이터 동기화와 장애 대응, 운영 지식도 추가로 필요하다. [PostgreSQL 병렬 쿼리](https://www.postgresql.org/docs/current/parallel-query.html)

따라서 이 단계에서 확인할 질문은 두 가지다. 반복되는 넓은 범위의 집계가 서비스의 중요한 부하인가. 그리고 이를 다른 저장 구조로 옮겼을 때 줄어드는 비용이 새로운 시스템을 운영하는 비용보다 큰가. 실제로 측정한 병목이 없다면, 기존 데이터베이스의 한계를 경험한 것처럼 적기보다 앞으로의 읽기 패턴을 근거로 검토 범위를 넓혔다고 설명하는 편이 정확하다.

{% comment %}
경험 보강 2 — OLAP을 검토한 계기가 실제 병목이었는지, 예상되는 조회 패턴이었는지 적는다. 기존 DB와 비교 실험을 하지 않았다면 그 사실을 유지한다. 처리량이나 지연시간은 검증 가능한 결과가 있을 때만 보완한다.
{% endcomment %}

## 3. 추가되는 이력이라고 해서 정정이 없는 것은 아니다

거래·이벤트 이력은 시간을 따라 추가되는 데이터로 모델링하기 좋다. 다만 체인에 기록된 사건과 분석 저장소에 적재한 행을 동일하게 취급해서는 안 된다.

먼저 무엇을 한 건으로 셀지 정해야 한다. Ethereum 계열에서 하나의 트랜잭션에는 여러 로그가 포함될 수 있고, ERC-20의 전송 이벤트는 거래 전체와는 다른 단위다. 거래 건수와 전송 이벤트 건수를 같은 집계로 다루면 데이터베이스가 빠르게 계산하더라도 결과의 의미가 달라진다. [Ethereum 트랜잭션 영수증과 로그](https://ethereum.org/developers/docs/apis/json-rpc/), [ERC-20 전송 이벤트](https://eips.ethereum.org/EIPS/eip-20)

최신 데이터의 확정 기준도 필요하다. Ethereum의 JSON-RPC는 `latest`, `safe`, `finalized`를 구분한다. 최신 블록을 얼마나 빨리 보여줄지에 따라 정정 가능성을 다루는 정책이 달라진다. 다른 체인에도 같은 기준을 그대로 적용할 수 있다고 전제해서는 안 된다. [Ethereum 블록 파라미터](https://ethereum.org/developers/docs/apis/json-rpc/)

수집 과정에도 정정이 생긴다. 같은 구간을 재시도하면 중복을 처리해야 하고, 누락된 구간을 채우거나 파싱 방식을 바꾸면 파생 데이터를 다시 계산해야 할 수 있다. 원본 사건이 그대로여도 저장소 안의 표현은 달라질 수 있다는 뜻이다.

이 때문에 후보를 비교할 때는 적재 속도와 함께 **같은 입력을 다시 처리해도 같은 결과로 돌아오는가**를 확인해야 한다. 원본에서는 중복을 제거했지만 이미 만들어진 합계에는 중복분이 남아 있다면, 원본 테이블의 상태만 확인해서는 정확성을 설명할 수 없다.

이 글의 분석 예시는 일정한 확정 기준을 통과한 사건을 사용하고, 사건의 식별과 재처리 규칙을 별도로 정의한다는 전제에 선다. 이 기준을 먼저 맞춰야 서로 다른 제품에서 얻은 건수와 합계를 비교할 수 있다.

## 4. 후보를 비교하는 기준은 기능과 유지 비용이다

대부분의 후보는 집계, JOIN, 갱신 중 여러 기능을 지원한다. 기능의 유무만으로 표를 채우면 실제 선택에 필요한 차이가 잘 드러나지 않는다. 같은 조회를 제공하기 위해 어떤 모델을 만들고, 그 결과를 어떻게 유지할 것인지까지 비교해야 한다.

아래 표에는 지금 이 선택을 설명하는 데 유용한 후보를 모았다. 실제 도입 당시의 후보 목록과 현재 문서로 보완한 비교는 경험을 추가하면서 구분할 예정이다.

| 후보 | 검토할 이유 | 함께 부담하거나 확인할 부분 |
| --- | --- | --- |
| PostgreSQL | 목록 조회, 관계 표현과 갱신을 익숙한 SQL 환경에서 구현 | 넓은 집계와 인덱스 유지의 자원 사용, 다른 요청과의 경쟁 |
| ClickHouse | 누적 이력의 열 단위 읽기와 반복 집계의 사전 계산 | 조회에 맞는 정렬, 파생 테이블 유지, 중복·정정 처리 |
| StarRocks | 다중 테이블 분석과 키 기반 상태 갱신을 함께 검토 | JOIN 분산과 메모리, 상태 인덱스, MV 갱신과 재작성 조건 |
| Apache Doris | 분석용 테이블과 UPSERT가 필요한 모델을 함께 검토 | 테이블 모델별 갱신 의미와 선택한 배포 구성의 운영 비용 |
| Iceberg + Trino | 파일 기반 이력을 여러 분석 작업에서 공유 | 카탈로그와 파일 관리, 적재·정리 작업, API 조회 지연 |
| Parquet + DuckDB | 공개 데이터 분석과 기준 결과를 간단히 재현 | 지속 적재와 서비스 동시 조회를 처리할 구성의 별도 검증 |

### PostgreSQL: 별도 분석 저장소가 필요한지 판단할 기준점

주소와 기간을 조건으로 하는 조회, 데이터 갱신, 관계 표현을 한 환경에서 다룰 수 있다는 점은 출발점으로서 의미가 있다. 적절한 인덱스는 필요한 행을 찾는 비용을 줄이지만 저장 공간과 쓰기 작업의 부담도 추가한다. [PostgreSQL 인덱스](https://www.postgresql.org/docs/current/indexes.html)

초기 요구가 제한적이고 기존 구성으로 목표를 만족한다면, 익숙한 저장소를 유지하는 것이 합리적일 수 있다. 비교해야 할 것은 제품 이름으로 예상한 한계보다 실제 조회가 읽는 범위와 자원 사용이다. 분석 저장소를 추가하는 결정에는 데이터가 두 곳에 존재할 때의 동기화와 복구 작업도 포함된다.

### ClickHouse: 자주 읽을 형태를 미리 준비할 수 있는가

ClickHouse의 `MergeTree` 계열에서는 정렬된 데이터 part와 희소 인덱스를 이용해 읽을 범위를 줄인다. 주소별 목록과 토큰별 기간 집계가 서로 다른 정렬을 필요로 한다면, 어느 조회에 맞춰 데이터를 배치할지 판단해야 한다. 하나의 정렬 키가 모든 접근을 같은 수준으로 빠르게 만든다고 기대할 수는 없다. [MergeTree의 저장과 인덱스](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/mergetree)

반복 집계에는 증분 Materialized View(MV)를 검토할 수 있다. 새로 들어온 데이터 묶음에 계산을 적용하고, 그 결과를 별도 대상 테이블에 적재하는 방식이다. 집계 테이블을 읽을 때는 엔진과 집계 함수에 맞게 부분 결과를 다시 합쳐야 할 수 있다. [ClickHouse 증분 MV](https://clickhouse.com/docs/concepts/features/materialized-views/incremental-materialized-view)

이 구조가 매력적인 조건은 분명하다. 자주 실행할 질문을 알고 있고, 미리 계산한 결과를 여러 번 사용할 수 있을 때다. 대신 적재 과정의 계산, 추가 저장 공간, 과거 구간의 재생성은 선택의 비용에 포함해야 한다.

### StarRocks와 Apache Doris: 결합과 갱신을 중요한 요구로 둘 때

StarRocks에서 살펴볼 지점은 여러 관계를 SQL로 표현하고, 반복되는 JOIN·집계에 비동기 MV를 활용하는 방식이다. 조건에 맞으면 원본 테이블을 대상으로 한 쿼리를 MV를 읽는 계획으로 재작성할 수 있다. 애플리케이션이 조회용 테이블을 일일이 선택하는 작업을 줄일 가능성이 있지만, 재작성 범위와 갱신 주기, 허용할 데이터 지연을 검증해야 한다. [StarRocks MV 쿼리 재작성](https://docs.starrocks.io/docs/using_starrocks/async_mv/use_cases/query_rewrite_with_materialized_views/)

최신 상태를 읽는 모델도 비교 대상이다. StarRocks의 Primary Key 테이블은 같은 키의 새 데이터를 반영할 때 이전 행을 읽기 대상에서 제외하는 구조를 사용한다. 키별 현재 상태를 조회하는 SQL을 단순하게 유지하는 데 유용할 수 있지만, 키 인덱스와 갱신에 필요한 자원은 함께 평가해야 한다. [StarRocks Primary Key 테이블](https://docs.starrocks.io/docs/table_design/table_types/primary_key_table/)

Apache Doris 역시 Unique Key 모델에서 UPSERT와 부분 갱신을 제공한다. 갱신과 분석을 함께 다루는 후보라는 점에서 검토할 만하다. StarRocks와 기능 이름이 비슷하더라도 모델의 제약과 배포 구성, 운영 방식은 각각 확인해야 한다. [Apache Doris 갱신 모델](https://doris.apache.org/docs/3.x/data-operate/update/update-overview/)

초기 요구를 안정적인 이력 집계로 대부분 표현할 수 있다면 이런 기능의 비중은 상대적으로 작을 수 있다. 반대로 새 관계를 자주 결합하고 최신 상태를 반복해서 읽는다면 평가의 중심으로 올라온다. 기능이 있다는 사실과 그 기능이 현재의 문제를 줄여준다는 판단을 연결해야 한다.

### Iceberg·Trino와 DuckDB: 보관·공유·분석의 역할을 나눌 때

Iceberg는 데이터 파일을 테이블로 관리하는 형식이고, Trino는 이를 조회할 수 있는 엔진이다. 별도 데이터베이스 제품 하나와 완전히 같은 범주의 선택은 아니다. Trino의 Iceberg 커넥터는 데이터 파일에 대한 접근과 카탈로그를 필요로 한다. 장기 이력을 여러 엔진이 공유하는 구성을 검토할 때 의미가 있다. [Trino Iceberg 커넥터](https://trino.io/docs/current/connector/iceberg.html)

이 구성을 택해도 원본을 해석하고 정리하는 작업은 남는다. 블록이나 이벤트를 조회할 열로 변환하고, 중복과 정정 규칙을 적용하고, 파일과 파티션을 관리해야 한다. 데이터 레이크를 이용한다는 설명만으로 API에 필요한 데이터 모델이나 가공 과정이 없어지는 것은 아니다. 파일 배치와 캐시, 조회 범위가 응답시간에 미치는 영향도 따로 측정해야 한다.

Parquet와 DuckDB는 공개 데이터로 분석을 시작하거나 기준 결과를 재현하는 도구로 유용하다. DuckDB는 Parquet를 직접 읽으며 필요한 열과 필터를 스캔에 반영할 수 있다. 이 편의성을 서비스 전체의 적합성으로 확대하려면 지속 적재와 동시 조회를 포함한 구성을 검증해야 한다. [DuckDB Parquet 지원](https://duckdb.org/docs/current/data/parquet/overview)

이 후보들은 일부 역할을 나누어 함께 사용할 수도 있다. 원본 보관, 반복 분석, 서비스 응답을 한 시스템에 맡길지 분리할지는 별도의 설계 결정이다. 계층을 늘렸을 때 얻는 이점과 데이터 이동·일관성 관리의 비용을 함께 비교해야 한다.

{% comment %}
경험 보강 3 — 당시 실제로 검토한 후보, 직접 시험한 후보, 글을 준비하면서 추가한 후보를 구분한다. 익숙한 기술, 도입 일정, 운영 가능 범위 등 공개할 수 있는 선택 조건을 덧붙인다. 현재 기능을 과거 선택의 근거로 소급하지 않는다.

## 5. JOIN을 줄이는 설계는 계산 시점을 앞당긴다

초기에 세웠던 가정은 필요한 조회를 어느 정도 예측할 수 있다는 것이었다. 거래·이벤트의 속성을 조회 목적에 맞게 모아두고 반복 통계를 준비하면, 요청마다 관계를 다시 결합하는 작업을 줄일 수 있다고 보았다.

여기서 넓은 테이블, 즉 wide table은 조회에 함께 필요한 속성을 한 행에 모은 모델이다. 시각, 자산 식별자, 송수신 주소, 수량을 한 사건의 속성으로 두는 식이다. 행이 많이 쌓인 큰 테이블과 열을 넓게 구성한 테이블은 구분할 필요가 있으며, 모든 조회를 하나의 테이블에 넣어야 한다는 뜻도 아니다.

예를 들어 설명용 모델에서는 같은 전송 이력에서 다음과 같이 서로 다른 읽기 형태를 만들 수 있다.

| 읽기 형태 | 한 행 또는 집계 상태가 나타내는 것 | 줄이려는 조회 작업 |
| --- | --- | --- |
| 사건 이력 | 식별 가능한 전송 사건 하나 | 원본 분석과 재처리의 기준 유지 |
| 주소 중심의 조회 데이터 | 특정 주소와 사건의 연결 | 주소별 목록의 필터와 정렬 |
| 토큰·일자별 집계 데이터 | 같은 토큰과 날짜의 건수·수량 또는 부분 집계 | 반복되는 기간 통계의 계산 |

이 표는 실제 운영 스키마가 아니라 읽기 요구에 따른 분리의 예다. 특히 한 사건을 송신·수신 주소 관점으로 각각 저장했다면, 그 테이블 전체를 그대로 더한 값은 사건 단위의 합계와 다를 수 있다. 한 행의 의미를 정하는 작업이 비정규화보다 먼저다.

ClickHouse도 여러 테이블의 JOIN을 지원한다. 조회 시점의 JOIN을 줄이는 선택은 JOIN을 구현할 수 없어서 생기는 필수 조건이 아니다. 관계가 비교적 단순하고 변경 빈도가 낮은 경우, 반복되는 결합 비용을 적재와 사전 가공으로 옮길 수 있다는 설계적 판단이다. [ClickHouse JOIN과 비정규화 지침](https://clickhouse.com/docs/concepts/best-practices/minimize-optimize-joins)

이 접근의 비용은 요구가 바뀔 때 드러난다. 새 필터에 필요한 속성을 저장하지 않았다면 테이블을 보완하고 과거 구간을 채워야 할 수 있다. 자주 바뀌는 라벨을 모든 사건에 복제했다면, 현재 라벨로 과거 이력을 다시 해석할 때 갱신 범위를 고민해야 한다.

증분 MV에도 같은 구분이 필요하다. JOIN을 포함한 ClickHouse 증분 MV는 소스 테이블에 삽입될 때 실행되며, JOIN 상대 테이블의 변경만으로 기존 결과가 자동 갱신되지는 않는다. 가격이나 분류를 미리 붙였다면 어떤 변경이 과거 결과의 재계산을 요구하는지 별도로 정해야 한다. [증분 MV의 JOIN 동작](https://clickhouse.com/docs/concepts/features/materialized-views/incremental-materialized-view)

따라서 JOIN을 줄였다는 결과만으로 설계 비용을 설명할 수는 없다. 조회에서 절약한 만큼 적재, 저장, 정정과 모델 변경에서 무엇을 부담하는지 함께 기록해야 한다. 반복되는 읽기의 이점이 이 유지 비용을 감당할 만큼 큰지가 선택의 기준이다.

{% comment %}
경험 보강 4 — 초기에는 왜 JOIN이 많지 않을 것으로 보았는지 적는다. 조회 종류, 미리 준비할 수 있었던 속성, 변경 빈도에 대한 당시 가정을 설명한다. 어떤 새 요구가 이 가정을 바꿨는지는 한두 문장만 남기고 구체적인 재평가는 2편으로 넘긴다.

## 6. ClickHouse를 선택한 판단이 성립하는 조건

초기의 선택을 기술적 조건으로 정리하면 세 가지로 모인다.

첫째, 주요 부하가 누적 이력에서 필요한 열과 범위를 읽는 작업이다. 이 경우 열 지향 저장과 조회에 맞는 정렬을 선택 근거로 삼을 수 있다.

둘째, 반복해서 실행할 질문을 어느 정도 예측할 수 있다. 자주 쓰는 집계와 조회 데이터를 미리 준비하고 여러 요청에서 재사용할 수 있다면, 적재 때 수행한 작업이 읽기 비용을 줄이는 데 기여한다.

셋째, 그 모델을 유지하는 비용을 감당할 수 있다. 파생 테이블의 추가 저장, 데이터 반영 지연, 재처리와 새 요구 반영까지 포함한 판단이어야 한다. 이 조건은 제품의 기능 목록보다 서비스 요구와 운영 여건에 가깝다.

이 기준에서 ClickHouse는 초기 설계와 연결되는 선택이었다. 여기서 선택의 근거는 모든 후보보다 빠르다는 순위가 아니라, 당시 중심에 둔 읽기 패턴과 데이터를 준비하는 방식의 적합성이다. StarRocks보다 단일 테이블 집계가 항상 빠르다는 결론도 이 설명에서 도출할 수는 없다. 그런 비교에는 동일한 결과 기준과 각 제품에 맞춘 모델, 실제 측정이 필요하다.

선택 후에도 따로 검증할 부분은 남는다. 예를 들어 `ReplacingMergeTree`에 같은 정렬 키의 여러 버전을 넣으면 백그라운드 병합 전에는 중복이 보일 수 있다. 정확한 최신 행을 읽으려면 `FINAL` 등 필요한 처리까지 포함해 조회 비용을 평가해야 한다. 또한 원본에서 나중에 일어난 병합이 증분 집계에 이미 반영된 중복분까지 되돌려준다고 가정해서는 안 된다. [ReplacingMergeTree의 조회 의미](https://clickhouse.com/docs/concepts/features/operations/update/replacing-merge-tree), [증분 MV의 처리 범위](https://clickhouse.com/docs/concepts/features/materialized-views/incremental-materialized-view)

최신 상태를 계속 갱신하는 일이나 복잡한 관계를 조합하는 일이 주요 부하가 되면 세 조건의 비중도 달라진다. 그때는 현재 버전의 ClickHouse가 제공하는 선택지와 다른 제품의 모델을 같은 요구에 놓고 다시 비교해야 한다.

{% comment %}
경험 보강 5 — 실제 선택에 가장 큰 영향을 준 이유 하나와 받아들이기로 했던 비용 하나를 적는다. 이미 검증했던 사실, 설계 단계의 예상, 도입 뒤 알게 된 제약을 나누어 쓴다. 사용하지 않은 MV나 엔진을 실제 운영한 것처럼 바꾸지 않는다.
{% endcomment %}

## 7. 선택의 근거를 검증하고, 다음 요구에 대비한다

제품의 특성을 설명하는 것과 해당 서비스에서 선택이 타당했음을 입증하는 것은 다르다. 이를 이어주려면 서비스가 실제로 묻는 질문과 같은 결과 기준을 가진 검증이 필요하다. 아래는 성능 결과가 아니라, 경험이나 개인 실험을 추가할 때 사용할 비교 항목이다.

| 검증 항목 | 확인할 질문 |
| --- | --- |
| 정확성 | 중복 입력과 과거 구간 재처리 전후에 사건 수와 합계가 같은가 |
| 수량과 단위 | 큰 정수의 원형과 계산 정밀도를 보존하며, 서로 다른 자산의 수량을 섞지 않는가 |
| 조회 지연 | 목록·집계·최신 상태별 목표를 만족하며, p95·p99 지연은 어떤가 |
| 데이터 반영 | 입력이 조회에 보이기까지 얼마나 걸리며, 지연을 감지할 수 있는가 |
| 동시 작업 | 지속 적재와 과거 데이터 재처리 중에도 조회 요구를 만족하는가 |
| 유지 비용 | 새 필터·집계가 생길 때 바꿔야 할 테이블·가공 작업·API SQL은 무엇인가 |

성능을 비교한다면 버전, 하드웨어, 데이터 분포, 캐시, 복제와 내구성 조건을 함께 기록해야 한다. 한 후보에는 미리 계산한 테이블을 사용하고 다른 후보에는 매번 원본을 계산하게 했다면, 조회 시간 외에도 사전 계산과 갱신 비용을 포함해야 한다. 원하는 답을 만드는 데 필요한 전체 작업을 비교하는 셈이다.

또한 평균 지연시간 하나만으로 서비스 조회를 평가하기는 어렵다. 자주 쓰이는 주소나 특정 토큰에 데이터가 몰린 상황, 새 데이터가 계속 들어오는 상황, 과거 구간을 다시 적재하는 상황에서 느려지는 요청을 따로 확인해야 한다.

{% comment %}
경험 보강 6 — 실제로 확인한 결과가 있으면 조건과 함께 추가한다. 수치 없이도 확인한 동작과 남은 한계를 설명할 수 있다. 실행하지 않은 항목은 계획으로 남기고, 무엇이 확인되면 선택을 바꿀지도 적는다.
{% endcomment %}

초기에는 이력이 쌓이는 방식과 반복되는 조회를 중심으로 문제를 정의했다. 그 조건에서는 필요한 데이터를 미리 준비하고 ClickHouse에서 읽는 접근에 설계적 근거가 있었다. 다만 예측할 수 있는 조회가 얼마나 오래 유지되는지, 미리 붙인 정보가 얼마나 자주 바뀌는지는 데이터의 양만으로 판단할 수 없는 변수였다.

가격 데이터가 들어오고 분류 기준이나 조회 조합이 늘어나면, 같은 원본을 두고도 유지해야 할 결과가 달라진다. 다음 글에서는 이런 변화가 JOIN과 최신 상태 관리의 비중을 어떻게 높이는지, 지금 새로 시작한다면 왜 StarRocks를 우선 검토하고 싶은지 살펴본다.
